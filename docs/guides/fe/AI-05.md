### Reapertura correctiva y recuperación parcial del 19/07/2026

La prueba autenticada efímera inicial, en modo Demo y sin llamadas LLM, ejecutó
`POST /api/plan/generate` con 63 tópicos para 7, 15 y 30 días. Los tres casos
respondieron `500 AI_DEMO_FIXTURE_INVALID`.

La causa está en `createDemoPlan()`: ordena primero por nivel K global y luego
reparte los tópicos en round-robin. `parseGeneratedPlan()` exige capítulos
ascendentes y orden K1 → K2 → K3 dentro de cada capítulo. El fixture y el
parser, por tanto, implementan semánticas incompatibles.

La corrección posterior ordenó por capítulo y K, distribuyó segmentos contiguos
con `floor/ceil` y completó las invariantes de método, duración, título,
dificultad y cobertura. `npm --prefix frontend run test:plan` pasa 9/9: parser
y Route Handler real responden correctamente para 7, 15 y 30 días sin red.

**Gate recuperado:** el parser estricto demuestra `200`, sesiones no vacías,
densidad calculada, método `theory`, duración 90, título máximo 80, dificultad
coherente, cero duplicados/omisiones y cobertura completa en 7, 15 y 30 días.
El provider stub demuestra fallback por disponibilidad con un evento por
candidato; `AI_INVALID_RESPONSE` se detiene sin segundo candidato.

## Addendum Correctivo Obligatorio

AI-05 no puede limitarse a reemplazar una función por otra. La inspección del
código real encontró cuatro contratos incompatibles que deben corregirse como
parte de la futura implementación:

1. **La key BYOK no alcanza hoy los consumidores reales.** AI-03 conserva
   `byokApiKey` dentro de `AiSettingsClient`. Al salir de
   `/settings/ai` ese componente se desmonta, por lo que `/setup`,
   `/session` y `/practice` nunca pueden enviar la key a sus Route Handlers.
   AI-05 debe elevar únicamente esa referencia al layout autenticado, en estado
   React volátil. Esto sustituye la regla histórica de “borrar al navegar” solo
   para navegación interna del dashboard; siguen prohibidos Supabase,
   `localStorage`, `sessionStorage`, cookies, logs y respuestas.
2. **La reserva Managed ocurre antes de terminar de construir el cliente.**
   `resolveAiRuntime()` reserva cuota y recién después ejecuta
   `createProviderRuntime()`. Si la construcción falla, queda un evento
   `QUOTA_RESERVED` pendiente sin que haya existido una llamada facturable. La
   creación local del SDK, que no hace red, debe ocurrir antes de reservar.
3. **Las rutas actuales eligen y recorren modelos por su cuenta.** Los seis
   endpoints usan `createModelRuntimes()`; `/api/plan/generate` acepta además
   `model_provider` desde el body. Esa cascada contradice la preferencia
   allowlisted de `user_ai_settings` y puede facturar a un proveedor diferente
   del que el usuario configuró. AI-05 centraliza una cascada del mismo
   proveedor, ordenada por versión, y crea una reserva/evento por candidato;
   también elimina el selector legacy de `/setup`.
4. **Los parsers legacy confían en casts o completan datos inválidos.**
   Teoría, quiz, plan y práctica contienen `as Tipo` después de `JSON.parse`;
   Practice Evaluate transforma campos ausentes en defaults que parecen éxito.
   La misma validación runtime debe aceptar tanto la respuesta real como el
   fixture Demo antes de persistir. Un payload incompatible termina como error
   auditado, nunca como colección vacía o feedback inventado.

| Operación correctiva | Archivo / anchor real |
|---|---|
| **CREAR** contrato HTTP sin secretos | `frontend/lib/ai/http-contract.ts` |
| **CREAR** proveedor React efímero para el dashboard | `frontend/components/ai/ai-session-provider.tsx` |
| **CREAR** ejecutor JSON server-only | `frontend/lib/ai/execute-json.ts` |
| **MODIFICAR** construcción previa a reserva y desactivar retries ocultos | `frontend/lib/ai/runtime.ts`, `frontend/lib/ai/model-cascade.ts` |

| **ELIMINAR** bypass server-only sin consumidores | `frontend/lib/openai.ts` |
| **CREAR** fixture remoto no facturable | `frontend/scripts/verify-ai05-runtime.mjs` |

**Gate del addendum:** no habilitar Managed ni afirmar que AI-05 está
implementada si queda una importación de `createModelRuntimes()` en cualquiera
de los seis endpoints, si una reserva puede quedar pendiente por construir el
SDK, si el body de plan aún decide el modelo o si BYOK necesita almacenamiento
persistente para funcionar.

### Auditoría Correctiva Posterior: Plan y Política de Modelos

La prueba real con 63 tópicos encontró dos contratos que esta guía no
reconcilió correctamente:

1. `UP-04` conservaba una densidad fija de `3-5` tópicos y un mínimo de `2` por
   sesión. Para 30 días se requieren 60 sesiones, de modo que 63 tópicos solo
   permiten 1 o 2 por sesión. AI-05 endureció el parser, pero no auditó de nuevo
   esas instrucciones del productor. El resultado correcto fue
   `AI_INVALID_RESPONSE`; aceptar el payload habría persistido duplicados o una
   cantidad incorrecta de sesiones.
2. AI-02 ordenaba conservar `createModelRuntimes()` y su cascada compartida.
   AI-05 ordenó eliminarla para evitar llamadas ocultas y cargos no auditados.
   Por tanto, la pérdida del fallback no fue causada por la UI de Settings: fue
   una decisión explícita de esta guía que contradice la política anterior.

La misma prueba aclaró una ambigüedad de UP-04: el orden K1 → K2 → K3 se
aplica dentro de cada capítulo. Aplicarlo globalmente entraría en conflicto con
la regla de mantener juntos FL-1, FL-2, etc. El validador final ordena sesiones
por día/turno, impide regresar a un capítulo anterior y evita que un capítulo
vuelva de K2/K3 a un nivel K menor.

El prompt de plan debe usar una densidad derivada:

```typescript
const minTopicsPerSession = Math.max(
  1,
  Math.floor(totalTopics / totalSessions),
);
const maxTopicsPerSession = Math.max(
  minTopicsPerSession,
  Math.ceil(totalTopics / totalSessions),
);
```

No se debe compensar un `AI_INVALID_RESPONSE` agregando dos outputs de 16 000
tokens a una sola reserva: con el límite Managed predeterminado de 50 000
tokens diarios, el peor caso puede bloquear la operación antes de contactar al
proveedor. Plan conserva un intento JSON por modelo. El fallback de
disponibilidad crea otra reserva y otro evento antes de llamar al candidato
siguiente.

La cascada central corregida no restaura el loop legacy. Cumple:

- Settings selecciona el proveedor; el body de cada feature no lo sustituye.
- Los candidatos pertenecen al mismo proveedor y a una allowlist ordenada.
- Cada llamada externa tiene reserva, finalización, modelo y tokens propios.
- Un error de disponibilidad puede avanzar al siguiente candidato.
- Un rechazo del contrato no avanza silenciosamente a otro modelo, porque la
  llamada anterior ya consumió tokens. Este comportamiento coincide con el
  patrón de referencia auditado, que detiene la cascada cuando su validador
  rechaza la salida.
- `maxRetries` del SDK permanece en cero; la aplicación controla cada intento.

El orden canónico confirmado es por versión descendente:
`gemini-3.5-flash`, `gemini-3.1-pro-preview`,
`gemini-3.1-flash-lite`, `gemini-3-pro-preview`,
`gemini-3-flash-preview`, `gemini-2.5-pro` y
`gemini-2.5-flash`. El catálogo remoto se verifica sin generar contenido y sin
imprimir la key.

**Gate adicional:** la cascada solo está reconciliada si un fixture demuestra
dos eventos separados para modelo fallido y modelo exitoso, ambos finalizados
y sin `QUOTA_RESERVED` pendiente.

**Límite de memoria:** JavaScript no permite garantizar “borrado físico” de un
string. `clearByokApiKey()` elimina referencias controladas y vuelve el valor
elegible para garbage collection; no debe describirse como zeroization. Una
key en memoria también puede ser leída por JavaScript malicioso ejecutado en
el mismo origen, por lo que PR-03A deberá auditar CSP y dependencias antes de
producción.

## Sección 1: 🎓 Introducción y Fundamentos Conceptuales

### Analogía profesional

Imagina una torre de control. Cada pista representa una feature —plan,
teoría, quiz, evaluación o práctica— y cada avión es una petición. Hoy cada
pista decide por su cuenta qué proveedor usar, cuánto esperar y qué hacer si
falla. Aunque cada controlador sea competente, no existe una única autoridad
que compruebe combustible, permiso de despegue y registro del vuelo.

El runtime de AI-02 es esa torre central. Antes del despegue autentica al dueño,
lee su modo, selecciona un modelo allowlisted y, si la plataforma paga el vuelo,
reserva la cuota de forma atómica. Después, AI-04 exige cerrar el evento con el
consumo real o con un código de error estable. AI-05 conecta las seis pistas a
esa secuencia sin cambiar sus contratos pedagógicos ni su persistencia.

Demo no es una pista falsa: es un simulador determinista que atraviesa los
mismos validadores y consumidores, pero no contacta un proveedor. BYOK es un
permiso temporal que el navegador entrega solo a la torre del mismo origen.
La torre nunca lo archiva, lo imprime ni lo devuelve.

### Conceptos React, Next.js y runtime relevantes

- **Server Component que compone un Client Provider:** el dashboard layout
  continúa autenticando y leyendo perfil en servidor. Puede renderizar
  `AiSessionProvider` como frontera cliente sin convertir todo el layout en
  Client Component ni enviar datos de Supabase como JavaScript adicional.
- **Hidratación y memoria React:** la key nace después de la hidratación, por
  interacción del usuario. El layout compartido permanece montado durante
  navegación cliente entre rutas del mismo grupo; recargar, cerrar sesión o
  abandonar el grupo desmonta el provider y pierde la referencia.
- **Route Handlers públicos por naturaleza:** `proxy.ts` protege páginas, pero
  no reemplaza autorización de API. Cada `POST` conserva `auth.getUser()`,
  ownership, validación del body y respuestas JSON `401/403/404` propias.
- **Runtime Node.js explícito:** el SDK OpenAI-compatible, AbortController,
  keys de servidor y cliente admin permanecen en módulos `server-only` y
  Route Handlers con `export const runtime = "nodejs"`.
- **Reserva de peor caso y finalización real:** si una operación permite dos
  intentos por JSON inválido, Managed reserva prompt y output para ambos antes
  del primer request. La finalización suma los tokens reales de todos los
  intentos con el mismo `eventId`.
- **Idempotencia acotada:** un `eventId` se genera una vez por petición HTTP y
  se reutiliza en los intentos internos. El cache en memoria del quiz sigue
  siendo best-effort; no debe confundirse con idempotencia durable entre
  lambdas o después de un redeploy.
- **Structured Outputs y JSON mode:** Practice Generate conserva su JSON
  Schema estricto. Las demás rutas usan JSON mode, incluyen una instrucción
  explícita de producir JSON y validan la forma en runtime antes de persistir.
- **Errores públicos frente a errores internos:** el cliente recibe códigos
  estables y mensajes en español. Nunca recibe `error.message`, status crudo,
  cuerpo del proveedor, prompt, headers, key, modelo alternativo ni stack.

### Documentación de runtime consultada

- `frontend/node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`:

  proceso ni de Edge Runtime.
- [OpenAI Chat Completions](https://platform.openai.com/docs/api-reference/chat/create):

  tolerar ausencia y validar la respuesta.
- [Gemini mediante librerías OpenAI](https://ai.google.dev/gemini-api/docs/openai):
  la compatibilidad usa `baseURL` OpenAI-compatible y admite respuestas
  estructuradas. AI-05 conserva Chat Completions porque el runtime soporta
  Gemini y OpenAI con el mismo cliente; no migra modelos ni APIs.
- [Supabase: RLS y privilegios](https://supabase.com/docs/guides/database/postgres/row-level-security):
  RLS decide filas y los privilegios/`EXECUTE` deciden alcance de operaciones.
  El alcance original reutilizó las RPC de AI-02/04. El cierre correctivo del
  20/07/2026 agregó tres migraciones para snapshot privado, adaptación atómica
  y leases cercados; una instalación nueva necesita las 16 migraciones vigentes.

`max_completion_tokens`. Esta guía conserva temporalmente `max_tokens` porque

real de compatibilidad; AI-05 no mezcla esa migración con el control de cuota.

            Exec->>LLM: una llamada o retry JSON explícito
            LLM-->>Exec: JSON + usage opcional
            Exec->>DB: finalize_managed_ai_usage
        end
    else BYOK
        Runtime-->>Exec: provider/model/cliente con key efímera
        Exec->>LLM: llamada con timeout
        LLM-->>Exec: JSON + usage opcional
        Exec->>DB: insertar evento BYOK sin key
    end
    Exec-->>API: valor validado o error público
    API->>DB: persistir dominio solo si corresponde
    API-->>UI: contrato existente
    UI-->>User: resultado o mensaje recuperable
~~~

### Matriz productor → validador → persistencia → consumidor

| Feature | Productor / parser | Persistencia de dominio | Consumidor | Fallo de IA |
|---|---|---|---|---|
| `plan` | `GeneratedPlan` + `validateGeneratedPlan` | se guarda después por `/api/plan/save` | `/plan` | error HTTP; no existe plan parcial |
| `theory` | `TheoryTopicContent[]` estricto | `sessions.theory_content` | `TheoryPanel` | error HTTP; no sobrescribe cache válido |
| `quiz` | 10–12 `QuizQuestion` | cache de proceso best-effort | `QuizCard` | error HTTP; no cachea colección inválida |
| `evaluate` | análisis cualitativo estricto | respuestas + sesión completada | `FeedbackPanel` | fallback determinista; evaluación sigue |
| `practice_generate` | `LlmPracticeResponse` por discriminante | `practice_exercises` | páginas Practice/Bug Lab | error HTTP; no persiste escenario inválido |
| `practice_evaluate` | `PracticeFeedback` exacto por criterios | `practice_submissions` | feedback/solución | error HTTP; no crea submission |

### Presupuesto y timeout por feature

| Feature | Timeout | Output máximo por intento | Intentos externos | Reserva Managed |
|---|---:|---:|---:|---:|
| plan | 90–180 s según días | 16 000 | 1 | prompt + 16 000 |
| theory | 90 s | 6 000 | 1 | prompt + 6 000 |
| quiz | 60 s | 5 000 | 1 | prompt + 5 000 |
| evaluate | 45 s | 4 000 | 1 | prompt + 4 000 |
| practice_generate | 90 s | 6 000 | 1 | prompt + 6 000 |
| practice_evaluate | 90 s | 6 000 | 2 solo por JSON inválido | dos prompts + 12 000 |

  path: string,
  init?: RequestInit,
) => Promise<Response>;

interface AiSessionContextValue {
  byokApiKey: string;
  setByokApiKey: (value: string) => void;
  clearByokApiKey: () => void;
  aiFetch: AiFetch;
}

const AiSessionContext = createContext<AiSessionContextValue | null>(null);

export function AiSessionProvider({ children }: { children: ReactNode }) {
  const [byokApiKey, setByokApiKeyState] = useState("");

  const setByokApiKey = useCallback((value: string) => {
    const sanitized = value
      .replace(/[\r\n]/g, "")
      .slice(0, MAX_BYOK_API_KEY_LENGTH);
    setByokApiKeyState(sanitized);
  }, []);

  const clearByokApiKey = useCallback(() => {
    setByokApiKeyState("");
  }, []);

  const aiFetch = useCallback<AiFetch>(
    async (path, init) => {
      const url = new URL(path, window.location.origin);
      const isSameOrigin =
        url.origin === window.location.origin &&
        url.username.length === 0 &&
        url.password.length === 0;
      const method = (init?.method ?? "GET").toUpperCase();

      if (
        !isSameOrigin ||
        !isAiFeaturePath(url.pathname) ||
        url.search.length > 0 ||
        method !== "POST"
      ) {
        throw new Error("AI_ROUTE_NOT_ALLOWED");
      }

      const headers = new Headers(init?.headers);
      headers.delete(BYOK_API_KEY_HEADER);
      const key = byokApiKey.trim();
      if (key.length > 0) {
        headers.set(BYOK_API_KEY_HEADER, key);
      }

      return fetch(url.pathname, {
        ...init,
        credentials: "same-origin",
        headers,
        method,
      });
    },
    [byokApiKey],
  );

  const value = useMemo<AiSessionContextValue>(
    () => ({
      byokApiKey,
      setByokApiKey,
      clearByokApiKey,
      aiFetch,
    }),
    [aiFetch, byokApiKey, clearByokApiKey, setByokApiKey],
  );

  return (
    <AiSessionContext.Provider value={value}>
      {children}
    </AiSessionContext.Provider>
  );
}

export function useAiSession(): AiSessionContextValue {
  const context = useContext(AiSessionContext);
  if (!context) {
    throw new Error("useAiSession requiere AiSessionProvider");
  }
  return context;
}

  code: AiPublicErrorCode,
  error: string,
  reason?: AiQuotaBlockReason,
): AiExecutionFailure {
  return {
    ok: false,
    status,
    body: {
      error,
      code,
      ...(reason ? { reason } : {}),
    },
  };
}

function readByokHeader(request: Request): ByokHeaderResult {
  const rawValue = request.headers.get(BYOK_API_KEY_HEADER);
  if (rawValue === null) return { ok: true };

  const value = rawValue.trim();
  if (
    value.length === 0 ||
    value.length > MAX_BYOK_API_KEY_LENGTH ||
    /[\r\n]/.test(value)
  ) {
    return failure(
      400,
      "AI_BYOK_KEY_INVALID",
      "La API key temporal tiene un formato inválido.",
    );
  }

  return { ok: true, value };
}

function estimateTokens(text: string): number {
  return text.length === 0 ? 0 : Math.max(1, Math.ceil(text.length / 3));
}

function validUsage(value: number | null | undefined): number | null {
  return typeof value === "number" &&
    Number.isInteger(value) &&
    value >= 0
    ? value
    : null;
}

export async function executeAiJson<T>(
  options: ExecuteAiJsonOptions<T>,
): Promise<AiExecutionResult<T>> {
  if (
    options.userPrompts.length === 0 ||
    options.userPrompts.length > 2 ||
    !Number.isInteger(options.maxCompletionTokensPerAttempt) ||
    options.maxCompletionTokensPerAttempt <= 0
  ) {
    return failure(
      500,
      "AI_RUNTIME_INVALID",
      "La operación de IA no pudo prepararse.",
    );
  }

  const byok = readByokHeader(options.request);
  if (!byok.ok) return byok;

  const eventId = crypto.randomUUID();
  const reservationPrompt = options.userPrompts
    .map((userPrompt) => options.systemPrompt + "\n" + userPrompt)
    .join("\n");
  const reservationCompletionTokens =
    options.maxCompletionTokensPerAttempt * options.userPrompts.length;

  let resolved: ResolvedAiRuntime;
  try {
    resolved = await resolveAiRuntime({
      userId: options.userId,
      eventId,
      feature: options.feature,
      promptText: reservationPrompt,
      maxCompletionTokens: reservationCompletionTokens,
      timeoutMs: options.timeoutMs,
      byokApiKey: byok.value,
    });
  } catch {
    return failure(
      503,
      "AI_QUOTA_UNAVAILABLE",
      "No se pudo preparar la operación de IA. Intenta de nuevo.",
    );
  }

  if (resolved.status === "blocked") {
    const quota = QUOTA_FAILURES[resolved.reason];
    return failure(429, quota.code, quota.error, resolved.reason);
  }

  if (resolved.status === "duplicate") {
    return failure(
      409,
      "AI_REQUEST_DUPLICATE",
      "Esta operación de IA ya fue procesada.",
    );
  }

  if (resolved.status === "unavailable") {
    return unavailableFailure(resolved.reason);
  }

  if (resolved.status === "demo") {
    let value: T | null = null;
    try {
      value = options.parse(options.createDemoRaw());
    } catch {
      value = null;
    }

    if (value === null) {
      const usageFailure = await recordOrFail({
        eventId,
        userId: options.userId,
        feature: options.feature,
        mode: "demo",
        provider: null,
        model: null,
        status: "error",
        errorCode: "AI_DEMO_FIXTURE_INVALID",
        fallbackPromptTokens: 0,
        fallbackCompletionTokens: 0,
      });
      if (usageFailure) return usageFailure;

      return failure(
        500,
        "AI_DEMO_FIXTURE_INVALID",
        "El fixture educativo de Demo no cumple el contrato.",
      );
    }

    const usageFailure = await recordOrFail({
      eventId,
      userId: options.userId,
      feature: options.feature,
      mode: "demo",
      provider: null,
      model: null,
      status: "success",
      fallbackPromptTokens: 0,
      fallbackCompletionTokens: 0,
    });
    if (usageFailure) return usageFailure;

    return {
      ok: true,
      value,
      mode: "demo",
      provider: null,
      model: null,
      tokensUsed: 0,
    };
  }

  let promptTokens = 0;
  let completionTokens = 0;

  for (
    let attemptIndex = 0;
    attemptIndex < options.userPrompts.length;
    attemptIndex += 1
  ) {
    const userPrompt = options.userPrompts[attemptIndex];
    const fallbackPromptTokens = estimateTokens(
      options.systemPrompt + "\n" + userPrompt,
    );
    const controller = new AbortController();
    const timeoutId = setTimeout(
      () => controller.abort(),
      options.timeoutMs,
    );

    try {
      const params: CompletionParams = {
        model: resolved.model,
        messages: [
          { role: "system", content: options.systemPrompt },
          { role: "user", content: userPrompt },
        ],
        max_tokens: options.maxCompletionTokensPerAttempt,
        response_format: { type: "json_object" },
        ...(options.tuning?.(resolved.provider) ?? {}),
      };

      const completion = await resolved.runtime.client.chat.completions.create(
        params,
        { signal: controller.signal },
      );
      const rawText = completion.choices[0]?.message?.content ?? "";

      promptTokens +=
        validUsage(completion.usage?.prompt_tokens) ?? fallbackPromptTokens;
      completionTokens +=
        validUsage(completion.usage?.completion_tokens) ??
        estimateTokens(rawText);

      let value: T | null = null;
      try {
        value = rawText.length > 0 ? options.parse(rawText) : null;
      } catch {
        value = null;
      }

      if (value !== null) {
        const usageFailure = await recordOrFail({
          eventId,
          userId: options.userId,
          feature: options.feature,
          mode: resolved.mode,
          provider: resolved.provider,
          model: resolved.model,
          status: "success",
          providerUsage: {
            prompt_tokens: promptTokens,
            completion_tokens: completionTokens,
          },
          fallbackPromptTokens: promptTokens,
          fallbackCompletionTokens: completionTokens,
        });
        if (usageFailure) return usageFailure;

        return {
          ok: true,
          value,
          mode: resolved.mode,
          provider: resolved.provider,
          model: resolved.model,
          tokensUsed: promptTokens + completionTokens,
        };
      }
    } catch (caught) {
      promptTokens += fallbackPromptTokens;
      const timedOut =
        controller.signal.aborted || isModelTimeout(caught);
      const internalCode = timedOut
        ? "AI_PROVIDER_TIMEOUT"
        : "AI_PROVIDER_UNAVAILABLE";
      const usageFailure = await recordOrFail({
        eventId,
        userId: options.userId,
        feature: options.feature,
        mode: resolved.mode,
        provider: resolved.provider,
        model: resolved.model,
        status: "error",
        errorCode: internalCode,
        providerUsage: {
          prompt_tokens: promptTokens,
          completion_tokens: completionTokens,
        },
        fallbackPromptTokens: promptTokens,
        fallbackCompletionTokens: completionTokens,
      });
      if (usageFailure) return usageFailure;

      return timedOut
        ? failure(
            504,
            "AI_PROVIDER_TIMEOUT",
            "El proveedor de IA no respondió a tiempo.",
          )
        : failure(
            502,
            "AI_PROVIDER_UNAVAILABLE",
            "El proveedor de IA no pudo completar la solicitud.",
          );
    } finally {
      clearTimeout(timeoutId);
    }
  }

  const usageFailure = await recordOrFail({
    eventId,
    userId: options.userId,
    feature: options.feature,
    mode: resolved.mode,
    provider: resolved.provider,
    model: resolved.model,
    status: "error",
    errorCode: "AI_INVALID_RESPONSE",
    providerUsage: {
      prompt_tokens: promptTokens,
      completion_tokens: completionTokens,
    },
    fallbackPromptTokens: promptTokens,
    fallbackCompletionTokens: completionTokens,
  });
  if (usageFailure) return usageFailure;

  return failure(
    502,
    "AI_INVALID_RESPONSE",
    "El proveedor devolvió una respuesta incompatible.",
  );
}
~~~

### Por qué esta secuencia es fail-closed

1. El Route Handler autentica y valida ownership antes del ejecutor.
2. El ejecutor rechaza headers BYOK vacíos, largos o con saltos de línea.
3. Managed reserva el peor caso antes de la red.
4. Demo atraviesa exactamente `options.parse`; un fixture roto queda auditado
   como error de cero tokens.
5. Cada respuesta real suma usage de los reintentos JSON del mismo modelo. Si
   el proveedor no lo entrega, usa una estimación conservadora por caracteres.
   Un fallback de modelo finaliza ese evento y crea otro antes de llamar.
6. Si falla `recordAiUsage()`, no se devuelve éxito. En Managed, AI-04 hará
   visible una reserva pendiente en vez de ocultarla.
7. El catch nunca serializa `caught`. Solo clasifica status de disponibilidad
   (`404`, `408`, `409`, `429`, `5xx`, conexión o timeout) para decidir si puede
   avanzar; el cliente recibe siempre errores sanitizados.

**Entregable del Paso D:** una única secuencia
resolver → reservar candidato → llamar/fixture → validar → finalizar → fallback
auditable, reutilizable por las seis features y sin lógica de dominio.

function readStringList(
  value: unknown,
  minimum: number,
  maximum: number,
): string[] | null {
  if (
    !Array.isArray(value) ||
    value.length < minimum ||
    value.length > maximum ||
    !value.every(
      (item) => typeof item === "string" && item.trim().length > 0,
    )
  ) {
    return null;
  }

  return value;
}

function parsePracticeFeedback(
  rawText: string,
  expectedCriteria: string[],
): PracticeFeedback | null {
  const value = parseFirstJsonObject(rawText);
  if (
    !value ||
    typeof value.feedback_summary !== "string" ||
    value.feedback_summary.trim().length === 0 ||
    !Array.isArray(value.criteria_results) ||
    value.criteria_results.length !== expectedCriteria.length
  ) {
    return null;
  }

  const byCriterion = new Map<string, CriterionResult>();
  for (const item of value.criteria_results) {
    if (
      !isRecord(item) ||
      typeof item.criterion !== "string" ||
      !expectedCriteria.includes(item.criterion) ||
      byCriterion.has(item.criterion) ||
      typeof item.passed !== "boolean" ||
      typeof item.detail !== "string" ||
      item.detail.trim().length === 0
    ) {
      return null;
    }

    byCriterion.set(item.criterion, {
      criterion: item.criterion,
      passed: item.passed,
      detail: item.detail,
    });
  }

  const criteriaResults: CriterionResult[] = [];
  for (const criterion of expectedCriteria) {
    const result = byCriterion.get(criterion);
    if (!result) return null;
    criteriaResults.push(result);
  }

  const missingCases = readStringList(value.missing_cases, 0, 8);
  const strengths = readStringList(value.strengths, 1, 5);
  const improvements = readStringList(value.improvements, 1, 5);
  if (!missingCases || !strengths || !improvements) return null;

  return {
    feedback_summary: value.feedback_summary,
    criteria_results: criteriaResults,
    missing_cases: missingCases,
    strengths,
    improvements,
  };
}

### Matriz manual end-to-end

Usa una cuenta de prueba autenticada con documento, plan, sesión y ejercicio
propios. No exportes HAR ni captures el valor del header BYOK.

| Caso | Acción | Resultado esperado |
|---|---|---|
| Demo plan | Settings → Demo; generar plan | `200`, dos sesiones no vacías por día, títulos/resumen `[MODO DEMO]`, evento `plan/demo/success` con 0 tokens |
| Demo teoría | abrir sesión sin `theory_content` | contenido válido por cada código, `model_provider=demo`, persistencia y evento `theory` |
| Cache teoría | recargar sin `force` | `cached: true`, ningún evento nuevo |
| Demo quiz | iniciar quiz | 10-12 preguntas públicas, cuatro opciones, sin `correct`/`explanation`; snapshot privado durable y evento `quiz` |
| Replay quiz | recargar o repetir generación | mismo `attempt_id`, snapshot durable y ningún evento nuevo, incluso tras redeploy |
| Demo evaluate | enviar quiz completo | score/acción deterministas, answers + sesión + adaptación atómicos; un 100% omite IA cualitativa |
| Demo Practice Generate | generar cada uno de los cuatro tipos | shape válido, escenario marcado Demo, solución ausente del response, evento `practice_generate` |
| Demo Practice Evaluate | enviar una práctica | feedback simulado marcado, solution revelada después del insert, evento `practice_evaluate` |
| Managed éxito controlado | habilitar una cuota pequeña suficiente y ejecutar una feature | una reserva finalizada `success`; AI-04 aumenta actividad y cuota Managed |
| Managed límite 0 | configurar límite administrativamente en cuenta fixture y ejecutar | rutas generativas `429` con código estable; Session Evaluate conserva `200` determinista y muestra aviso |
| Managed concurrencia | ejecutar fixture AI-02 | no se supera cuota; `reserved + blocked` |
| BYOK preparada | elegir provider, modo BYOK y pegar key temporal | Settings la muestra solo dentro del input; no aparece en storage/cookies |
| BYOK navegación | navegar por Link desde Settings a setup/session/practice | la llamada real usa la key sin volver a pegarla y crea evento BYOK |
| BYOK recarga | recargar una página y volver a llamar | `400 AI_BYOK_KEY_REQUIRED`; no existe key recuperable |
| BYOK cambio provider/modo | guardar el cambio y volver | la key anterior queda vacía; se requiere una nueva |
| Logout | cerrar sesión con key cargada | contexto se limpia antes de sign-out; volver a entrar no recupera key |
| Provider timeout | usar un stub controlado que no responde | `504 AI_PROVIDER_TIMEOUT`, evento error sin mensaje crudo |
| JSON inválido | stub devuelve objeto truncado | una llamada en todas salvo Practice Evaluate; esta usa máximo dos y termina `502 AI_INVALID_RESPONSE` |
| Auditoría caída | simular fallo de finalización en entorno aislado | no se devuelve éxito LLM; AI-04 muestra reserva pendiente Managed |

La prueba con stub pertenece al entorno local/aislado. Nunca apuntes
`GEMINI_OPENAI_BASE_URL` a un host no confiable usando una key real; usa una
key ficticia y no ejecutes esa configuración contra producción.

### Fixtures de contrato que deben aceptar o rechazar

| Feature | Fixture válido | Fixture inválido | Resultado |
|---|---|---|---|
| plan | `sessions` exactas, coverage consistente | sesión vacía, tópico duplicado o código inventado | aceptar / `AI_INVALID_RESPONSE` |
| theory | todos los códigos, intro ≥50, summary ≥30 | código faltante, `key_concepts` vacío, enum K inválido | aceptar / rechazar |
| quiz | 10 preguntas, opciones a–d, correct distribuido | 9 preguntas, opción ausente, todas correct iguales | aceptar / rechazar |
| evaluate | mensaje, array de patrones válido, método y minutos | método desconocido, minutos negativos, patrón parcial | aceptar / fallback determinista |
| practice_generate | discriminante y solución por tipo | bug sin `observed_bug`, test cases con ≠6 filas | aceptar / rechazar |
| practice_evaluate | un resultado por criterio exacto | criterio omitido/duplicado, strengths vacío, enum inválido | aceptar / rechazar |

Demo es el fixture válido offline de cada feature: no basta con que compile; su
evento `success` demuestra que atravesó el mismo parser. Los casos inválidos
de proveedor se ejercitan con el stub controlado, no editando temporalmente
producción ni confiando en búsquedas de texto.

### Auth, ownership y límites HTTP

| Edge case | Resultado requerido |
|---|---|
| `POST` sin cookie | `401` JSON, nunca redirect HTML |
| UUID de sesión inválido | `400` antes de settings/runtime |
| documento/sesión/ejercicio ajeno | `403` o `404` según contrato histórico; ninguna reserva/evento |
| body requerido vacío, array vacío o campo ausente en plan/evaluaciones/Practice | `400`; ninguna llamada LLM; teoría y quiz sí permiten body vacío y usan `force=false` |
| `model_provider` en request de plan | `400` para detectar cliente legacy |
| tópicos menores que `objective_days × 2` | `422 PLAN_TOPICS_INSUFFICIENT`; no fixture ni proveedor |
| header BYOK vacío, con CR/LF o >512 | `400 AI_BYOK_KEY_INVALID` |
| BYOK sin header | `400 AI_BYOK_KEY_REQUIRED` |
| `aiFetch` con origen externo | excepción `AI_ROUTE_NOT_ALLOWED` antes de red |
| `aiFetch` con `/api/practice/generate-evil` | rechazo por path exacto |
| `aiFetch` con método distinto de `POST` o query string | rechazo antes de red; esos seis contratos usan body JSON |
| provider/model fuera de allowlist en DB | default allowlisted + `modelWasDefaulted`; nunca identificador libre al SDK |
| doble submission Practice | `409` antes del runtime y sin costo adicional |
| sesión ya completada | `409` antes del runtime |
| respuesta provider con error crudo/key reflejada | cliente solo ve DTO estable; no logs ni body crudo |

## Sección 7: 🚨 Troubleshooting — Problemas Comunes

| Problema | Causa probable | Solución |
|---|---|---|
| `useAiSession requiere AiSessionProvider` | el componente quedó fuera del route-group dashboard o el wrapper no rodea todo el shell | monta el provider en `(dashboard)/layout.tsx` sin convertirlo en Client Component |
| BYOK funciona en Settings pero no en Setup | se conservó el `useState` local de AI-03 o el caller sigue usando `fetch` | usa el contexto compartido y `aiFetch` en el consumidor exacto |
| La key sigue después de cambiar provider | Settings actualiza la fila pero no compara provider anterior/nuevo | llama `clearByokApiKey()` después del PATCH exitoso |
| `AI_ROUTE_NOT_ALLOWED` en una sesión válida | path dinámico no contiene UUID canónico o se pasó una URL ajena | usa el `sessionData.id` real y conserva la regex exacta |
| Plan responde `400` después del cambio | el cliente aún envía `model_provider` | elimina el campo de `StudyConfigData`, default, body y estado legacy |
| Plan responde `422 PLAN_TOPICS_INSUFFICIENT` | hay más sesiones requeridas que tópicos disponibles | reduce días o completa extracción; no generes sesiones vacías |
| AI-04 muestra reserva pendiente sin llamada | el SDK todavía se construye después de `reserve_ai_quota` | mueve `createProviderRuntime` antes de la RPC |
| Se cobra más de una vez por error de red | `maxRetries` del SDK no quedó en cero o la ruta conserva un loop propio | deja `maxRetries: 0`; el ejecutor central crea y audita un evento por candidato |
| `AI_USAGE_UNAVAILABLE` después de respuesta válida | falló insert/finalización de auditoría | revisa RPC/service role; no devuelvas éxito hasta cerrar o dejar pendiente visible |
| Practice Evaluate bloquea una cuota inesperadamente alta | la reserva suma dos outputs de 6 000 | comportamiento esperado del peor caso; ajusta cuotas administrativamente, no reduzcas el registro real |
| Demo genera `AI_DEMO_FIXTURE_INVALID` | `createDemoPlan()` ordena K global y distribuye round-robin, pero el parser exige capítulos ascendentes y K dentro del capítulo | corrige el fixture; no relajes el parser ni uses cast; repite 7, 15 y 30 días |
| Quiz Demo marca como correcta una opción falsa | se rotó la letra sin rotar el texto | usa `optionValues` del snippet final, donde `correctText` sigue a `correct` |
| La evaluación de sesión devuelve `429` y no guarda answers | se retornó directamente `ai.body` como en rutas generativas | Evaluate es best-effort: convierte el fallo en feedback visible y continúa persistencia |
| Practice devuelve `error.message` | quedó el catch legacy de `OpenAI.APIError` | delega el proveedor a `executeAiJson` y usa errores públicos |
| TypeScript rechaza `criteria_results` | el array conserva elementos `undefined` | construye un array nuevo y retorna `null` al primer criterio ausente |
| Build pasa pero BYOK termina en storage | solo se buscó código; no se probó navegador | inspecciona Application sin copiar valores y prueba recarga/logout/provider/mode |
| API anónima redirige a HTML | se delegó seguridad al Proxy | conserva `getUser()` dentro de cada Route Handler y responde `401` JSON |

### Decisiones que no se deben degradar

1. No volver a un selector de modelo por feature. Settings, el proveedor y la
   allowlist ordenada son la autoridad.
2. No persistir BYOK “para mejorar UX”. La pérdida al recargar es parte del
   contrato de seguridad.
3. No calcular cuota con `SELECT` en Next.js. Solo
   `reserve_ai_quota` autoriza Managed.
4. `429/5xx` solo puede avanzar mediante la cascada central, con nueva reserva
   y evento. `AI_INVALID_RESPONSE` no cambia de modelo automáticamente.
5. No usar `as TheoryTopicContent[]`, `as QuizQuestion[]` o
   `as PracticeFeedback` como validación.
6. No convertir JSON inválido en defaults que parezcan feedback real.
7. No permitir que un fallo cualitativo borre el score determinista de sesión.
8. No retornar `solution_json` desde Practice Generate.
9. No modificar migraciones AI-01/02/04 ya aplicadas.
10. No trasladar el control LLM a FastAPI: el BFF autenticado vive en Next.js.
